\section{Task 2: Spawning in Gazebo and Teleoperation}

The simulation world was based on the \texttt{shapes.sdf} example launched with
\texttt{gz sim shapes.sdf}. The original example contains multiple different shapes
arranged in neat rows. We used it as a basis, keeping the ground plane and sun while
copying and repositioning selected boxes and cylinders around the world. The other
shapes were removed to create the environment shown in Figure~\ref{fig:shapes-world}.

\begin{figure}[H]
    \centering
    \includegraphics[width=\textwidth]{images/shapes_world.png}
    \caption{World based on \texttt{gz sim shapes.sdf}, with a ground plane, sun, boxes, and cylinders.}
    \label{fig:shapes-world}
\end{figure}

\begin{figure}[H]
    \centering
    \includegraphics[width=\textwidth]{images/my_world.png}
    \caption{The final world used for the assignment, with a ground plane, sun, boxes, and cylinders.}
    \label{fig:my-world}
\end{figure}

The robot description was extended with collision and inertial properties.  These
properties allow Gazebo to detect contacts and simulate the robot's dynamics.
For example, the wheel collision geometry is defined as a cylinder:

\begin{lstlisting}[language=XACRO]
<collision>
  <geometry>
    <cylinder length="${length}" radius="${radius}" />
  </geometry>
</collision>
\end{lstlisting}

The wheel mass and principal moments of inertia are also specified.  The inertia
values use the standard formulas for a solid cylinder.

\begin{lstlisting}[language=XACRO]
<inertial>
  <mass value="${wheel_mass}" />
  <inertia
    ixx="${1/4 * wheel_mass * wheel_radius * wheel_radius
      + 1/12 * wheel_mass * wheel_length * wheel_length}"
    iyy="${1/4 * wheel_mass * wheel_radius * wheel_radius
      + 1/12 * wheel_mass * wheel_length * wheel_length}"
    izz="${1/2 * wheel_mass * wheel_radius * wheel_radius}"
    ixy="0" ixz="0" iyz="0" />
</inertial>
\end{lstlisting}
This is also done for the body, and caster wheel, using the appropriate formulas for a box and a solid sphere.  

The caster wheel was given a low friction coefficient so that it can rotate and
follow the robot without significantly resisting its motion:

\begin{lstlisting}[language=XACRO]
<gazebo reference="caster_wheel">
  <mu1>0.1</mu1>
  <mu2>0.1</mu2>
</gazebo>
\end{lstlisting}

The Gazebo DiffDrive system was added to convert velocity commands on
\texttt{cmd\_vel} into motion of the two drive wheels.  The wheel separation,
wheel radius, and joint names are taken from the xacro parameters:

\begin{lstlisting}[language=XACRO]
<plugin filename="gz-sim-diff-drive-system"
        name="gz::sim::systems::DiffDrive">
  <left_joint>chassis_to_left_wheel</left_joint>
  <right_joint>chassis_to_right_wheel</right_joint>
  <wheel_separation>${chassis_width}</wheel_separation>
  <wheel_radius>${wheel_radius}</wheel_radius>
  <topic>cmd_vel</topic>
</plugin>
\end{lstlisting}

Gazebo now publishes the joint states directly using its JointStatePublisher
system, so the separate ROS joint-state-publisher node is no longer needed:

\begin{lstlisting}[language=XACRO]
<plugin filename="gz-sim-joint-state-publisher-system"
        name="gz::sim::systems::JointStatePublisher" />
\end{lstlisting}

\subsection{ROS--Gazebo topic bridges}

The \texttt{ros\_gz\_bridge} configuration connects the ROS and Gazebo topics.
Velocity commands travel from ROS to Gazebo; clock, joint states, odometry,
transforms, and laser scans travel in the opposite direction.

\begin{table}[H]
\centering
\small
\begin{tabular}{@{}lllll@{}}
\toprule
ROS topic & Gazebo topic & ROS type & Gazebo type & Direction \\
\midrule
\texttt{cmd\_vel} & \texttt{cmd\_vel} & \texttt{Twist} & \texttt{Twist} & ROS--GZ \\
\texttt{clock} & \texttt{clock} & \texttt{Clock} & \texttt{Clock} & GZ--ROS \\
\texttt{joint\_states} & \texttt{.../joint\_state} & \texttt{JointState} & \texttt{Model} & GZ--ROS \\
\texttt{odom} & \texttt{odom} & \texttt{Odometry} & \texttt{Odometry} & GZ--ROS \\

\caption{Topics bridged between ROS 2 and Gazebo.}
\label{tab:topic-bridges}

The resulting communication graph is shown in Figure~\ref{fig:rosgraph}.  The
teleoperation node sends velocity commands through the bridge to Gazebo.  Gazebo
publishes the simulated clock, joint states, odometry, transforms, and laser
scan, which are then forwarded to ROS for RViz and other ROS nodes.

\begin{figure}[H]

For example the yaml part of the bridge configuration for the \texttt{cmd\_vel} topic is shown below:

\begin{lstlisting}[language=YAML]
- ros_topic: cmd_vel
  gz_topic: cmd_vel
  ros_type: geometry_msgs/Twist
  gz_type: geometry_msgs/Twist
  direction: ROS--GZ
\end{lstlisting}

\subsection{Launch configuration}

The launch file starts Gazebo with the custom world, publishes the robot
description, spawns the robot from the \texttt{robot\_description} topic, and
starts the configured topic bridge.  RViz and all relevant nodes use simulation
time.  Teleoperation is provided by \texttt{teleop\_twist\_keyboard}, which
publishes velocity commands to \texttt{cmd\_vel}.  The separate joint state
publisher is retired because Gazebo now provides those messages.

The joint-state-publisher node was removed from the launch file.  Joint states
are instead generated by the Gazebo plugin and bridged to ROS:

\begin{lstlisting}[language=XACRO]
<!-- Joint states are published by Gazebo. -->
<node pkg="robot_state_publisher"
      exec="robot_state_publisher"
      name="robot_state_publisher">
  <param name="robot_description"
         value="$(command 'xacro $(var urdf_path)')" />
  <param name="use_sim_time" value="true" />
</node>
\end{lstlisting}

Gazebo is launched with the custom world, and the robot is spawned from the
\texttt{robot\_description} topic.  The bridge receives its configuration from
the YAML file described above:

\begin{lstlisting}[language=XACRO]
<executable name="gz_sim"
            cmd="gz sim -r $(var world_path)"
            output="screen" />
<node pkg="ros_gz_sim" exec="create"
      args="-topic robot_description" />
<node pkg="ros_gz_bridge" exec="parameter_bridge">
  <param name="config_file"
         value="$(var bridge_config_path)" />
  <param name="use_sim_time" value="true" />
</node>
\end{lstlisting}

Finally, keyboard teleoperation is started in a separate terminal.  Its
velocity commands are sent to the DiffDrive plugin through \texttt{cmd\_vel}:

\begin{lstlisting}[language=XACRO]
<executable name="teleop_twist_keyboard"
  cmd="xterm -e ros2 run teleop_twist_keyboard
       teleop_twist_keyboard"
  output="screen" />
\end{lstlisting}

\section{Problems Encountered and Solutions}

The implementation involved a few configuration and formatting errors.  The
main issues and how they were resolved are summarized below.

\begin{enumerate}
  \item Xacro parameters were initially written with parentheses, for example
  \texttt{\$(body\_width)}.  The resulting ``Unknown substitution command''
  error led us to check the xacro substitution syntax.  Replacing the
  parentheses with curly braces, \texttt{\$\{body\_width\}}, fixed the issue.

  \item It was unclear where the Gazebo contact-coefficient tag belonged in
  the URDF.  The class slides and the Gazebo URDF tutorial explained the
  \texttt{<gazebo>} tag, but not its placement.  An LLM suggested putting it
  inside \texttt{<robot>}; we tested this suggestion, and the caster friction
  settings then worked as expected.

  \item A comment in the xacro file caused a compilation error.  Since the
  comment contained a colon, it was removed to test whether it was involved.
  The error disappeared, so the unnecessary comment was left out.

  \item RViz reported that the inertia element was missing the \texttt{ixx}
  attribute and could not parse the link inertial data.  Comparing the XML with
  the URDF format showed that the inertia values had been written as child
  elements.  They were changed to attributes, for example
  \texttt{<inertia ixx="..." iyy="..." izz="..." ixy="0" ixz="0" iyz="0"/>}.

  \item RViz initially did not display the wheel transforms.  Running
  \texttt{gz topic -l} showed both \texttt{joint\_states} and
  \texttt{/world/world\_demo/model/my\_robot/joint\_state}.  We compared these
  names with the bridge configuration and changed \texttt{gz\_topic\_name} to
  the full Gazebo topic path.  The joint states then reached ROS and the wheel
  transforms appeared in RViz.

  \item The lidar visualization appeared in Gazebo but remained fixed at the
  origin, and Gazebo reported that the lidar entity for \texttt{/scan} could
  not be found, even though messages were being published on that topic. 
  \begin{figure}[H]
    \centering
    \includegraphics[width=0.6\textwidth]{images/gazebo_lidar_bug.png}
    \caption{The lidar visualization in Gazebo, fixed at the origin.}
    \label{fig:gazebo-lidar-bug}
  \end{figure}
  The problem was caused by the Gazebo GUI being initialized before the lidar was
  available.  To ensure that the GUI starts only after Gazebo has finished
  initializing, the XML launch file was refactored as a Python launch file,
  which supports waiting for the server process before starting the GUI.
\end{enumerate}
